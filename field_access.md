# field_access.md — programmatic access to monitoring fields

`lbmmon_json` prints every monitoring packet as JSON. Some
customers will want to *act* on individual fields — feed a
counter into a dashboard, trip an alert on a threshold, ignore
records from a particular source, and so on. Parsing the emitted
JSON with a downstream tool works, but is wasteful when the
protobuf message has already been decoded.

This document is a guide that shows the
representative shapes of field access using the C++ protobuf
API `bld.sh` already generates under `generated/`. The examples
assume you are extending `lbmmon_json.cc` — the natural place
is inside the passthrough callback, right after the
`ParseFromArray` call succeeds, before (or instead of) the
`MessageToJsonString` call.

## Two API choices

The `.proto` schemas that describe UM monitoring data are
published by Informatica; anything that decodes them programmatically
is doing so against a public schema. There are two reasonable
starting points:

**C++ — generated by `bld.sh` (what this program uses).** `protoc
--cpp_out` produces typed classes with accessors like
`msg.stats().context().fragments_unrecoverably_lost()`. This
matches the language of `lbmmon_json.cc` and lets you drop
field-access code directly into the existing passthrough
callback with no re-parsing. This code path has *not* been
tested by UM QA; the codegen and library are Google's, and
Informatica's contribution is publishing the `.proto` files.

**C — shipped with UM.** The customer install includes
`protobuf-c`-generated headers under
`$LBM/include/lbm/gen/*.pb-c.h`
(`ums_mon.pb-c.h`, `ump_mon.pb-c.h`, `dro_mon.pb-c.h`, …)
along with `libprotobuf-c.so`. This code path *is* covered by
UM's QA, and Doxygen reference documentation is generated from
those headers. It's the right choice if you'd rather build a
from-scratch monitoring consumer against officially-supported
UM APIs — a `protobuf_c_message_unpack()` call replaces
`ParseFromArray`, and generated `Lbmmon__Ums_Mon_msg__…`
struct fields replace the C++ accessors. If you go this route,
you don't need the `.proto` fetch / `protoc` step in `bld.sh`
at all; the headers are already on disk.

The rest of this doc uses the C++ form.

## Accessor conventions (C++)

For a `.proto` field `some_counter` on message `MyMsg`, `protoc
--cpp_out` generates:

| Field kind        | Accessor                                    |
|-------------------|---------------------------------------------|
| scalar            | `msg.some_counter()`                        |
| submessage        | `msg.some_sub()` (const ref); `msg.has_some_sub()` for presence |
| repeated scalar   | `msg.items_size()`, `msg.items(i)`, or range-for over `msg.items()` |
| repeated message  | same shape; each element is a const ref     |
| oneof group       | `msg.<oneof>_case()` returns a tag enum; then call the matching submessage accessor |

Field names in the generated code are the exact names from the
`.proto` file (lowercased where the `.proto` uses CamelCase for
message names, but scalar / submessage field names in the UM
monitoring schemas are already snake_case). When in doubt, open
`generated/<name>.pb.h` and search for the field.

The passthrough callback in `lbmmon_json.cc` already gives you a
parsed C++ object as `m` inside `decode_payload<Msg>()`. The
snippets below show *what to do with `m`*, not the callback
plumbing around it. They are written as if pasted into the
callback just after `ParseFromArray` returned true.

## Example 1: LBT-RM unrecoverable loss (UMS receiver)

`UMSMonMsg` covers Source, Receiver, Event-Queue, Context,
Receiver-Topic, and Wildcard-Receiver records — the payload
shape is the same; which submessages are populated depends on
which `packet_type` triggered emission. For a receiver-side
packet, the interesting counters live under
`stats.receiver_transports`, which is a repeated list because a
single receiver can be attached to multiple sources on multiple
transport types.

The transport-specific stats are inside a `oneof TransportType`,
so you dispatch on the case enum before reading them. This
example reads three LBT-RM counters:

- `msgs_rcved` — messages received on this transport session.
  Always nonzero on a healthy receiver, so it's the counter
  used to demonstrate that field access is actually working.
- `unrecovered_txw` — message dropped out of the transmission
  window before it could be recovered.
- `unrecovered_tmo` — NAK-retry timed out.

The two `unrecovered_*` counters both contribute to what the
receiving application sees as `LBM_MSG_UNRECOVERABLE_LOSS`;
they should be zero on a well-behaved network.

```cpp
// m is a decoded lbmmon::UMSMonMsg.
using UMS = lbmmon::UMSMonMsg;
using RT  = UMS::Stats::ReceiverTransport;

if (m.has_stats()) {
    for (const RT &rt : m.stats().receiver_transports()) {
        if (rt.TransportType_case() == RT::kLbtrm) {
            const auto &lbtrm = rt.lbtrm();
            fprintf(stderr,
                    "LBT-RM on %s: msgs_rcved=%llu "
                    "unrecovered_txw=%llu unrecovered_tmo=%llu\n",
                    rt.source_string().c_str(),
                    (unsigned long long)lbtrm.msgs_rcved(),
                    (unsigned long long)lbtrm.unrecovered_txw(),
                    (unsigned long long)lbtrm.unrecovered_tmo());
        }
    }
}
```

Notes:

- `TransportType_case()` returns the generated case enum
  (`kTcp`, `kLbtrm`, `kLbtru`, `kLbtipc`, `kLbtsmx`,
  `TRANSPORTTYPE_NOT_SET`). Calling `rt.lbtrm()` on a
  non-LBT-RM entry is defined but yields a default-constructed
  submessage — dispatching on the case first is what you want.
- `rt.source_string()` returns a `const std::string&` naming the
  source the receiver is attached to (transport session
  identifier); it's a natural key when correlating with logs.
- Aggregate context-level loss for the *whole* receiver context
  is separately reported as
  `m.stats().context().fragments_unrecoverably_lost()`.

## Example 2: Store — source-repository unrecoverable loss

`UMPMonMsg` is the Store's monitoring message. Per-source
statistics live under `stats.src_repo_stats` (one entry per
source the Store persists). The `uls` field is the Store's
unrecoverable-loss counter for that source — messages the Store
knows it lost and cannot deliver — and `topic_name` identifies
which source it belongs to.

```cpp
// m is a decoded lbmmon::UMPMonMsg.
using UMP = lbmmon::UMPMonMsg;

if (m.has_stats()) {
    for (const UMP::Stats::SrcRepoStat &s : m.stats().src_repo_stats()) {
        if (s.uls() > 0) {
            fprintf(stderr,
                    "Store src '%s' (regid=%u) reports uls=%llu\n",
                    s.topic_name().c_str(),
                    (unsigned)s.src_regid(),
                    (unsigned long long)s.uls());
        }
    }
}
```

The `SrcRepoStat` message has ~20 other fields (sequence
numbers, drops, ULB — unrecoverable loss burst, etc.) plus a
nested `SrcDiskStat` submessage; the pattern for any of them is
the same call shape as `s.uls()`.

## Example 3: DRO — endpoint-portal fragment receive rate

`DROMonMsg` describes the DRO's view of itself. `stats.local`
holds process-wide identity and topology data;
`stats.portals` is one entry per DRO portal, each of which is
either an `Endpoint` (connected to a UM topic-resolution
domain) or a `Peer` (linked to another DRO) via a `oneof
PortalType`. Endpoint portals expose separate receive and send
counter blocks. The example below reads the
"transport-topic fragments received" counter for each endpoint
portal, which is the natural signal for "traffic arriving from
the TRD."

```cpp
// m is a decoded lbmmon::DROMonMsg.
using DRO = lbmmon::DROMonMsg;
using P   = DRO::Stats::Portal;

if (m.has_stats()) {
    const auto &local = m.stats().local();
    for (const P &portal : m.stats().portals()) {
        if (portal.PortalType_case() == P::kEndpoint) {
            const auto &ep  = portal.endpoint();
            const auto &rcv = ep.receive();
            fprintf(stderr,
                    "DRO %s portal %u endpoint: fragments_rcvd=%llu\n",
                    local.gateway_name().c_str(),
                    (unsigned)portal.portal_index(),
                    (unsigned long long)rcv.transport_topic_fragments_rcvd());
        }
    }
}
```

Notes:

- `local.gateway_name()` and `local.gateway_id()` identify the
  DRO globally; useful when several DROs monitor to the same
  stream.
- `PortalType_case()` returns `kEndpoint`, `kPeer`, or
  `PORTALTYPE_NOT_SET`.
- The `Endpoint`'s `Receive` submessage has ~30 counters
  covering transport-topic, immediate-topic, immediate-topicless,
  and unicast paths; `Send` has a matching set. All follow the
  same accessor pattern.

## Extending the callback: where the work goes

`passthrough_cb` in `lbmmon_json.cc` currently:

1. Peels the packet type off the header.
2. Dispatches into `decode_payload<Msg>()` which calls
   `ParseFromArray` on the right generated class.
3. Serializes the parsed message to JSON and writes it to
   stdout.

A natural place to add per-field logic is a second helper
alongside `decode_payload` (or inside it, before the JSON
serialization runs). If your consumer only cares about a subset
of packet types, gate the work on the `type` switch that already
exists — for example, only inspect receiver-transport data when
`type == LBMMON_PACKET_TYPE_RECEIVER`.

Two operational reminders from `lbmmon_json.cc`'s own comments:

- The callback runs on `lbmmon`'s worker thread. Anything
  blocking or heavy-weight there (file writes, network I/O,
  synchronous DB calls) stalls the receive loop. For anything
  more than a counter update, hand the decoded values off to a
  queue and process them elsewhere.
- The parsed C++ object (`m` in the snippets above) is a local
  in the callback. If you need to keep any of its fields for
  later, copy them out (scalar fields copy cheaply; for a whole
  submessage, use `.CopyFrom(...)` into a member of your own
  object) — don't stash pointers or references.
